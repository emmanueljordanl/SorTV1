# Operación supervisada

Desde sortv1: SIMULATION `python -m app --simulate`; DIAGNOSTIC `python -m app --mode diagnostic`; PHYSICAL_AUTO `python -m app --mode physical`. DIAGNOSTIC necesita `--enable-actuators --dest N` para solicitar destino conocido sin IA; Pico conserva interlocks. Todos los logs distinguen modo y fuente. Simulación no valida aceptación.

Antes de rearme: resguardos, energía aislada, bandeja/rotor/trayecto vacíos, compuerta cerrada y sensores conocidos. Habilitar cadena y pulsar rearme físico; CHECK_HOME y LISTO. Un objeto seco de catálogo ≤100×100×150mm y≤200g por ciclo. No admitir húmedos, peligrosos, pilas, vidrio ni objetos no verificados. Peso no decide material.

Primer AUTO supervisado. Configurar admission_record y registrar inspección humana antes de introducir la pieza, para boot actual y **siguiente cycle** observado en UI (actual+1), con `python -m app.tools.admit --operator OPERADOR --boot BOOT --cycle NUM --single-object --dry-known-catalog --within-limits`. Archivo contiene operator, timestamp UNIX, boot, cycle y tres permisos humanos; vence120s y no vale para otro ciclo. IA no acredita catálogo ni seguridad. No intentar escribir el registro durante el breve timeout de INSPECT.

Desde READY/LISTO: comprobar admisión antes de cargar, abrir tapa (actuator power OFF), introducir una pieza, cerrar tapa y pulsar **ACTUATOR_ENABLE** físico. Cerrar tapa no reenergiza la cadena. READY espera seguro, outputs OFF, mientras power=false; no inicia WAIT_STABLE ni falla solo por esa ausencia. Con calibrated/lid/service/power/link/heartbeat válidos, gate cerrado, peso conocido y presencia puede comenzar WAIT_STABLE. Abrir tapa es carga normal únicamente en READY; en POSITIONING/DISPENSING/VERIFY_CLOSE la pérdida de potencia/guarda sigue siendo FAULT. No confundir ACTUATOR_ENABLE del latch físico con PHYSICAL_RESET de GPIO15.

Tiempos distintos: **TARGET** inspection p95≤1000 ms, calculado con `inspection_ms`; **CONFIGURED_BASELINE** HARD PI DEADLINE inicial 1750 ms en config/physical.json; **PICO WAIT_DECISION TIMEOUT** 2000 ms. Solo enteros `1..1750` son válidos, reservando MIN_DECISION_MARGIN_MS=250 para Pi→USB→Pico. Deadline expirado→REVIEW y el resultado tardío nunca envía SORT. El baseline1750 y el margen no son medidas: **PENDING_PHYSICAL_BENCHMARK** hasta Raspberry Pi real. No usar el target p95 como hard timeout.

FAULT/REVIEW/E-STOP/SERVICE/reinicio: parar servicio y aislar potencia, retirar/reparar y conciliar si corresponde; verificar trayecto vacío, guardas, compuerta e índice único. Restaurar guardas, iniciar servicio desarmado, ACTUATOR_ENABLE, soltar/pulsar PHYSICAL_RESET, CHECK_HOME y READY. Parar servicio deja expirar heartbeat; power_feedback por sí solo no identifica el E-STOP. CHECK_HOME verifica índice conocido estable, sin movimiento de búsqueda. Sin índice: aislar, reposicionar rotor manualmente, obtener un solo índice y repetir rearme. Ver ADR0002 y RECOVERY.

UI local: LISTO/PROCESANDO/REVISIÓN/FALLO y datos del último ciclo, tapa/servicio/potencia, llenado orientativo, almacenamiento, modelo y firmware. Consulta/exportación; conciliación por CLI con servicio parado. Paro individual no está instrumentado por GPIO propio: no inferirlo desde power_feedback.

La UI no habilita motores ni rearma. Un eventual botón «admit next object» es POST_MVP / OPTIONAL; la admisión actual permanece por CLI y no sustituye guardas. Al cerrar servicio se detiene serve_forever, se cierra el socket y se esperan los hilos; el puerto8080 queda disponible para reiniciar.

Solo DONE acredita destino/caída correctos + bandeja vacía estable + compuerta cerrada. ACK no cuenta. Incertidumbre de un objeto previamente admitido puede decidir RECHAZO hacia destino3; no es etiqueta entrenable. FULL/UNKNOWN bloquean destino sin reruteo. REVIEW exige retirar objeto y cerrar registro con potencia aislada. FAULT exige identificar causa antes de rearme.
